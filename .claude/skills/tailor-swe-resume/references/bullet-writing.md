# Writing impact bullets

A resume bullet earns its place by showing an outcome, not by listing a duty. The
reader wants to know: what did you do, with what, and what happened as a result.

## The pattern

**Action verb + what you did + technology/context + measurable result**

Not every bullet has a clean number, and forcing fake ones is worse than none —
but reach for real metrics from the master resume wherever they exist: latency,
throughput, users, revenue, time saved, error rate, test coverage, team size.

## Rewrite examples

Each pair below shows a weak, duty-style bullet and the impact-form rewrite. The
rewrite invents nothing — it surfaces detail that was already true.

**Example 1**
- Weak: "Responsible for the payments API."
- Strong: "Built and owned a payments API in Node.js and PostgreSQL handling 50k+
  daily transactions, cutting checkout errors 30%."

**Example 2**
- Weak: "Worked on the frontend using React."
- Strong: "Rebuilt the account dashboard in React and TypeScript, reducing initial
  load time from 4s to 1.2s and lifting engagement 18%."

**Example 3**
- Weak: "Helped improve test coverage."
- Strong: "Introduced a Jest + Playwright test suite that raised coverage from 45%
  to 85% and caught regressions before release."

**Example 4 (no hard metric available — still concrete)**
- Weak: "Involved in migrating to microservices."
- Strong: "Extracted the notification service from a Rails monolith into a
  standalone Go service, enabling independent deploys and on-call ownership."

## Tailoring the verbs and nouns to the job

- Use the **posting's vocabulary** for real work: if the job says "CI/CD
  pipelines" and the user set up GitHub Actions, describe it as building CI/CD
  pipelines with GitHub Actions.
- Lead with the accomplishment that matches the job's core responsibility. A
  backend-heavy posting should see the user's backend bullets first, even if their
  most recent work was frontend.
- Strong, specific verbs: built, designed, led, shipped, optimized, automated,
  scaled, migrated, debugged. Avoid "responsible for", "helped with", "worked on".

## Guardrails

- Every number and claim must come from the master resume or be confirmed by the
  user. If a metric isn't recorded, write a concrete non-numeric outcome rather
  than guessing a figure.
- Don't relabel a skill into one the user doesn't have to hit a keyword. Adjacent
  experience can be framed as transferable, not misrepresented.
